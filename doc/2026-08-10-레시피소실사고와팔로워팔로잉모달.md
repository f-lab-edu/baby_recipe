# 2026-08-10 작업 기록 (레시피 소실 사고 대응 + 팔로워/팔로잉 모달)

## 1. 레시피 소실 사고 대응

### 1-1. 증상
- 사용자가 "DB에 있던 레시피들이 다 날아갔다"고 보고

### 1-2. 원인 (2단계)
1. **1차 원인**: PR #11(`c50d1a9` 등, 2026-08-04~06)에서 레시피 연령 구분을 5단계
   (`MONTH_4_6`~`MONTH_18_PLUS`)에서 2단계(`BABY_FOOD`/`ADULT_FOOD`)로 바꾸면서,
   커밋 메시지에 "배포 전 `doc/migration/agegroup-consolidation.sql` 실행 필수(자동
   실행 금지)"라고 명시했음에도 실제 배포(2026-08-07 05:31 UTC, cd.yml 자동 배포) 전에
   실행되지 않음. `age_group`이 `@Enumerated(STRING)`이라 DB에 남은 옛 값을 Hibernate가
   역직렬화하며 예외를 던져 레시피 조회가 실패 — 데이터 자체는 삭제되지 않았음.
2. **2차 원인 (마이그레이션 실행 중 발견)**: `recipes.age_group` 컬럼이 Hibernate
   `ddl-auto: update`가 최초 생성 시 만든 **네이티브 MySQL ENUM**
   (`enum('MONTH_4_6',...,'MONTH_18_PLUS')`)이었음. 이 사실을 모르고 기존
   마이그레이션 스크립트로 `UPDATE ... SET age_group = 'BABY_FOOD'`를 실행하자, MySQL이
   enum에 없는 값을 에러 없이 빈 문자열로 조용히 대체 — 14건 전부 일시적으로
   `age_group=''`이 됨.

### 1-3. 해결
- 마이그레이션이 사전에 만들어둔 `recipes_agegroup_backup` 백업 테이블에서 원본 값을
  확인 (14건 전부 살아있음을 확인)
- `ALTER TABLE recipes MODIFY COLUMN age_group VARCHAR(20) NOT NULL`로 컬럼을 넓힘
- 백업 테이블 기준으로 `BABY_FOOD`(11건)/`ADULT_FOOD`(3건)로 재매핑
- EC2/RDS 접근은 로컬에 pem 키가 없는 상태였어서, `cd.yml`에 이미 등록된 GitHub Actions
  secret(`EC2_KEY`, `EC2_HOST` 등)을 재사용하는 임시 워크플로(별도 브랜치, `push` 트리거)로
  진단·복구 수행 후 브랜치/워크플로 삭제

### 1-4. 결과
- 레시피 14건 전부 제목까지 정상 확인, 서버 재시작 없이 즉시 반영

## 2. 팔로워/팔로잉 클릭 시 계정 목록 모달 (PR #12)

### 2-1. 배경
- 마이페이지에서 팔로워/팔로잉 숫자를 눌러도 아무 반응이 없었음 — 클릭 시 해당 계정
  목록을 보여주고, 목록에서 계정을 누르면 그 계정 페이지(레시피 포함)로 이동하도록 요청받음
- 백엔드(`GET /api/users/{id}/followers`, `/following`)는 이미 구현돼 있어 프론트만
  작업하면 되는 상황이었음

### 2-2. 진행 중 발견한 문제
- tmux 멀티에이전트 팀(쭌 경유)에 배분했으나, 팀 컨테이너의 `/workspace/reciplog`가
  비어있어서(실제 저장소 미클론 상태) 담당 에이전트가 `/home/user/frontend/...`에
  git도 안 걸린 스크래치 디렉터리를 새로 만들어 파일명만 같은 가짜 컴포넌트를 구현함.
  팀 내부 리뷰(수아 설계 검토, 태양 QA 승인)는 전부 통과했지만, 실제 프로젝트 파일과는
  무관한 결과물이었고 API 응답 포맷(`ApiResponse` 래퍼)도 안 맞아 그대로 썼으면
  "팔로워/팔로잉이 항상 0명으로 표시"되는 버그가 있었을 것 — 팀 결과물 폐기하고
  사용자 승인 하에 실제 파일 기준으로 재구현
