## 3. 채팅 기능 설계 및 구현 (플랜모드)

### 3-1. 배경
- `doc/2026-07-22-URL링크저장기능.md`에서 채팅 기능 설계를 시작했다가 "실시간 전송 방식 미결정"으로 보류된 상태였음
- 이번 세션에서 플랜모드로 재착수, Explore 에이전트 2개(백엔드/프론트엔드 컨벤션 조사) + Plan 에이전트 1개(구현 설계)를 병렬/순차로 활용해 상세 플랜 작성 후 구현까지 완료

### 3-2. 주요 결정 사항
- **전송 방식**: WebSocket + STOMP, Spring 내장 in-memory SimpleBroker (EC2 단일 인스턴스라 Redis 등 외부 브로커 불필요 — 배포 구조 문서 `2026-06-11-aws-deploy-progress.md` 확인 결과 로드밸런서/Redis 없음)
- **인증**: 별도 체계 신설 없이 기존 JWT를 STOMP CONNECT 프레임에서 재사용
- **채팅 가능 대상**: 팔로우 관계 필요 (한쪽이라도 팔로우 중이면 가능 — 스팸 방지)
- **데이터 구조**: 지금은 1:1만 쓰지만 **참여자 테이블(N:N) 구조로 처음부터 설계** — 나중에 그룹 채팅으로 확장할 때 컬럼 기반(`userA`/`userB`) 구조에서 마이그레이션하는 비용을 피하기 위함. 사용자가 "추천은 1:1인데 나중에 다중 채팅을 고려해야 할 것 같다"고 언급 → 참여자 테이블 방식이 v1 구현 비용은 거의 늘지 않으면서 확장 비용을 없애준다는 점을 설명하고 채택
- **읽음 확인/안읽은 메시지 뱃지**: v1 범위에서 제외, 나중에 추가 — 이번이 이 프로젝트 최초의 실시간 기능이라 리스크를 줄이기 위해 "메시지 송수신/저장이 안정적으로 동작하는지"부터 검증하는 것을 우선하기로 함

### 3-3. 백엔드 구현
| 파일 | 내용 |
|------|------|
| `domain/ChatRoom.java` | 참여자 정보를 담지 않는 순수 방 엔티티 |
| `domain/ChatParticipant.java` | 방-유저 조인 엔티티, `(chat_room_id, user_id)` unique 제약 |
| `domain/ChatMessage.java` | 메시지 엔티티 (읽음 컬럼 없음) |
| `repository/ChatRoomRepository.java` | 두 유저의 기존 1:1 방을 찾는 커스텀 JPQL (`findDirectRoomId`) |
| `repository/ChatParticipantRepository.java` | 참여자 여부 확인(`existsByChatRoomIdAndUserId`), 방별/유저별 참여자 조회 |
| `repository/ChatMessageRepository.java` | 메시지 페이지 조회, 마지막 메시지 조회 |
| `service/ChatService.java` | 방 생성/조회, 메시지 조회/전송, 팔로우 게이팅 + 참여자 인가 체크 |
| `controller/ChatController.java` | REST: 방 목록/생성, 메시지 히스토리 |
| `controller/ChatStompController.java` | STOMP: `/app/chat.send` 수신 → 저장 후 `/topic/chat.{roomId}`로 브로드캐스트, `@MessageExceptionHandler`로 에러 처리 |
| `config/StompChannelInterceptor.java` | CONNECT 프레임에서 JWT 검증 + Principal 설정, **SUBSCRIBE 프레임에서 참여자 여부 검증** (SimpleBroker의 `/topic` 구독은 기본 인가 체크가 없어서 별도 구현 필요했음) |
| `config/WebSocketConfig.java` | `/ws` 엔드포인트 등록(SockJS 미사용), SimpleBroker 설정 |
| `config/SecurityConfig.java` | `/ws/**` permitAll 추가 (브라우저가 핸드셰이크에 커스텀 헤더를 못 실어서 실제 인증은 STOMP 레벨에서 처리) |
| `build.gradle` | `spring-boot-starter-websocket` 추가 |

### 3-4. 프론트엔드 구현
| 파일 | 내용 |

| `src/App.jsx` | `/chat`, `/chat/:roomId` 라우트 추가 |

| `vite.config.js` | `/ws` 프록시 추가 (`ws: true`) |

### 3-5. 검증
- 백엔드: `./gradlew compileJava` 성공, 신규 `ChatServiceTest`(방 생성/재사용, 자기자신 채팅 예외, 팔로우 없음 예외, 참여자 아닌데 조회/전송 예외 등 6케이스) 전부 통과
- 프론트엔드: `npm run build` 성공
- **실 브라우저 E2E(두 유저 실시간 송수신 확인)는 보류** — 로컬 MySQL은 떠 있으나 `root` 비밀번호를 몰라 `application-local.yml` 구성이 안 되어 `./gradlew bootRun` 로컬 구동이 막힘 (지난 세션 `2026-07-22` 기록에서도 동일 이슈 확인됨). 로컬 DB 접속 정보 확보 또는 배포 후 확인이 필요하며, 이번 세션에서는 사용자가 "지금은 건너뛰기"로 결정
